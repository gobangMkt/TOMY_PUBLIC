# 검색 개선 평가·진단 (팀 배포판)

검색 인사이트 앱이 내보낸 JSON을 읽어 **무엇을 먼저 손볼지** 가리고, 고를 건을 진단한다. Claude가 이 스킬의 기준을 읽고 직접 판단한다.
- 평가는 스크립트(`scripts/evaluate.py`)가 계산한다. 숫자 기준은 JSON의 `rules`에 있고 앱이 정본이다. Claude가 문턱값을 바꾸거나 평가를 다시 매기지 않는다.
- 진단·제목안은 Claude가 쓴다. 근거는 SEO 지식(이하 KB): `~/.claude/search-review/knowledge/seo/`. 처음 한 번 이 스킬 폴더의 `knowledge/seo/`(씨앗)를 복사해 만든 **내 사본**이라 자유롭게 고치고 키운다.
- 마케팅 판단(타깃·카피·채널): **사용자의 마케팅 어시스턴트**. 이 스킬의 `knowledge/seo/`는 그 어시스턴트에 흡수시키는 지식 묶음이기도 하다.
- 사용자 설정: `~/.claude/search-review/config.md`. 진단 기록: `~/.claude/search-review/log/`. 둘 다 스킬을 업데이트해도 지워지지 않는다.

## 0. 처음 한 번: 설치 마무리
### 0-1. 도구 확인
`python --version`(3.9 이상). 없으면 `winget install Python.Python.3.12` 후 진행한다. 평가 스크립트는 표준 라이브러리만 쓴다. 사용자에게 묻지 않는다.

### 0-2. 마케팅 어시스턴트 지정
`~/.claude/search-review/config.md`가 없으면 먼저 `~/.claude/shortform-review/config.md`를 본다(릴스 스킬을 이미 설치했다면 거기에 어시스턴트 위치가 있다). 있으면 "같은 마케팅 어시스턴트를 쓸까요?"라고 확인하고 그대로 쓴다. 없으면 묻는다.
> 마케팅 판단을 맡을 본인 마케팅 어시스턴트가 어디 있나요? 폴더 경로나 Claude 스킬 이름을 알려주세요. 이 스킬에 든 SEO 지식을 그 어시스턴트에 더해서 키웁니다. 없으면 새로 만들어 드릴게요.
- 스킬 이름을 받으면 `~/.claude/skills/{이름}` 또는 현재 프로젝트 `.claude/skills/{이름}`, `.agents/skills/{이름}`에서 실제 폴더를 찾아 경로로 바꾼다. 못 찾으면 다시 묻는다.
- 어시스턴트가 없다고 하면 `~/.claude/marketing-assistant/`를 새로 만들고(입구 파일 `README.md` 한 장) 그곳을 쓴다.
- `config.md`에 적는다:
```
# search-review 설정
- 마케팅 어시스턴트: {절대 경로}
- 입구 파일: {SKILL.md / CLAUDE.md / README.md 중 실제 파일}
- 흡수한 SEO 지식 버전: 없음
- 검색 데이터 폴더: {내보낸 JSON이 저장되는 폴더. 모르면 다운로드 폴더}
```

### 0-3. SEO 지식 흡수
`knowledge/seo/INGEST.md` 절차대로 어시스턴트에 지식을 더한다. 기존 내용은 지우거나 고치지 않고 덧붙이기만 한다. 끝나면 결과를 보고한다.

### 0-4. 내 지식 사본 만들기
`~/.claude/search-review/knowledge/seo/`가 없으면 이 스킬 폴더의 `knowledge/seo/` 전체를 그 자리로 복사한다(묻지 않는다). 이후 진단은 사본만 읽고 쓴다.

## 1. 매번 시작할 때
1. `config.md`를 읽는다. 없으면 0-2부터. 사본(KB)이 없으면 0-4.
2. `knowledge/seo/MANIFEST.md`의 버전이 `config.md`의 "흡수한 버전"과 다르면 바뀐 파일만 `INGEST.md` 절차로 흡수한 뒤 본 작업으로 간다.

## 2. 데이터 받기
- 사용자가 JSON 경로를 주면 그걸 쓴다. 안 주면 `config.md`의 검색 데이터 폴더에서 `검색인사이트_*.json` 중 가장 최근 파일을 쓰고, 어느 파일을 읽었는지 말한다. 파일이 없으면 앱의 `데이터 내보내기` 버튼을 눌러 받으라고 안내한다.
- 파일 기간(`window`)이 28일보다 짧거나 오래됐으면(내보낸 지 2주 넘음) 한 줄로 알린다.

## 3. 평가
1. `python {스킬 폴더}/scripts/evaluate.py {JSON 경로} --out {임시 폴더}/평가결과.json`을 돌린다. 요약표(평가별 건수)와 시급·나중 상위 건이 나온다.
2. 평가 4단계의 뜻:

| 평가 | 할 일 | 뜻 |
|---|---|---|
| 시급 | 이번 주 안에 전부 | 색인 지연·제외, 큰 글·검색어의 급락, 큰 검색어에 우리 글이 몰림 |
| 나중 | 이번 달 안에 | 중간 규모 급락, 큰 글의 제목·노출 문제, 색인 확인 전 |
| 관찰 | 손대지 않고 다음 갱신 때 또 걸리는지 본다 | 작은 글의 문제, 노출이 거의 없는 글 |
| 문제 없음 | 없음 | 걸린 증상이 없다 |

3. 한 건은 평가를 하나만 받고 건수를 더하면 전체와 같다. 되찾을 클릭은 평가 기준이 아니다. 요약표를 그대로 보여주고, 시급 건이 한 주에 처리하기 많으면 `rules`의 문턱을 앱에서 올려야 한다고 알린다(여기서 바꾸지 않는다).
4. 같은 평가 안에서는 잃은 노출이 큰 순이다. 위에서부터 처리한다.

## 4. 진단
사용자가 고른 건(없으면 시급 상위 10건을 제안한다). **한 번에 10건까지.** 건마다 아래를 쓴다. 원인과 할 일의 근거는 KB에서 상황에 맞는 파일만 읽는다(`knowledge/seo/README.md`의 라우팅표).
- 진단 이름(15자 이내 명사형), 지표 목표(실제 숫자와 같은 순위 평균 포함, 60자 이내), 원인 1~3개(숫자로), 할 일 1~4개(담당자가 그대로 따라 할 수 있는 말).
- 평가가 `급락`이면 KB `google-traffic-drop-debugging.md`의 진단 순서(기간·검색 유형·페이지별 손실)를 먼저 따른다. 원인을 확정하기 전에 제목·본문을 일괄 수정하라고 하지 않는다.
- 제목 문제면 제목안 2~3개: 20~45자, 대표 검색어를 앞쪽 절반에, `[숫자·고유명사 훅] + [!/?] + [독자 이득]`, 이모지·낚시 표현 금지. 안마다 추천도(3 강력 추천·2 추천·1 시험, 안끼리 같은 점수 금지), 이유(두 문장 이내), 검증할 가설(한 줄), 예상 수치(근거가 있을 때만, 같은 순위 평균에서 보수적으로. 없으면 비운다).
- 글이 갈리면(같은 검색어에 글 여러 개) 남길 대표 글과 나머지의 처리(통합·301)를 주소로 적는다(KB `google-canonical-duplicates.md`).
- 색인 문제면 기다릴지·글을 고칠지·기술 조치할지 KB `google-index-status.md`의 판정표로 가른다. 구글이 공개하지 않은 기준(몇 주 뒤 개입)은 단정하지 않는다.
- 내부 용어(기회 점수·갈래·판정)는 쓰지 않는다. 진단은 담당자에게 그대로 나갈 수 있다.

## 5. 요청서 만들기
사용자가 "요청서 만들어줘"라고 하면 진단한 건을 `검색개선요청_{YYYYMMDD}.md`로 저장한다(위치는 사용자에게 묻는다). 건마다 대상(주소), 요청 한 문장, 지금 제목, 바꿀 제목, 할 일, 근거 숫자. **글을 직접 고치지 않는다.** 고치는 것은 담당자다.

## 6. 효과 재기
요청서를 만든 날 `~/.claude/search-review/log/{YYYYMMDD}.md`에 건별 기준 지표(노출·클릭·순위)를 적는다. 28일 뒤 새 JSON을 받으면 같은 건의 지금 값과 견줘 좋아짐·나빠짐·변화 없음을 말한다. 나아지지 않아 평가에 다시 걸리면 새로 진단한다.

## 7. 하지 않는 것
- 문턱값(`rules`)을 바꾸거나 평가를 임의로 다시 매기기
- 근거 없는 수치 단정, 한 검색 한 줄로 확인한 내용의 단정
- 진단에서 글 본문·제목을 승인 없이 일괄 수정하라고 안내하기
- 이 스킬 폴더 안 파일 수정(업데이트 때 덮어써진다). 고칠 것은 내 사본(KB)에 한다
- 회사 실측 수치를 KB에 적재하기
