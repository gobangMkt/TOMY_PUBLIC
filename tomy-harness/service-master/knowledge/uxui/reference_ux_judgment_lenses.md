# UX 고수의 3대 생각 도구 (판단 프레임워크)

출처: 사용자 제공 스크립트 (2026-07-14 수집)

핵심: "이거 무거운데/답답한데" 같은 모호한 피드백을 받았을 때, 감이 아니라 아래 3가지 렌즈로 원인을 진단해서 즉각 해결책을 매칭한다.

## ① 시선의 물리적 흐름 (Gaze Stream)
눈동자가 Z자/F자로 자연스럽게 흘러야 함. 위·아래·구석으로 갈팡질팡하면 그 디자인은 실패. **시선이 걸리는 "턱(장애물)"이 어디인지 찾아 제거**하는 게 핵심 스킬.
- 진단 질문: 이 화면에서 눈이 어디서 멈칫하는가?

## ② 뇌의 에너지 소모량 (Cognitive Load)
뇌는 게을러서 정보 유입 자체가 스트레스. **"글자를 읽어야만 이해되는가, 형태·색상만으로 직관적으로 아는가"**를 본다. 읽어야 아는 디자인일수록 무겁고 답답함.
- 진단 질문: 텍스트 없이 형태/색상만으로 의미가 전달되는가?

## ③ 단서(Affordance)의 명확성
"이건 누르는 버튼", "이건 옆으로 넘기는 슬라이드"라는 단서가 명확해야 함. 눌러야 할 게 안 눌리게 생겼거나, 텍스트일 뿐인데 버튼처럼 생기면 불합격.
- 진단 질문: 이 요소가 뭘 할 수 있는지 형태만 보고 알 수 있는가?

## 적용 방식
"답답하다/무겁다" 피드백 → 이 3개 렌즈를 순서대로 통과시켜 원인 특정 → 원인에 맞는 구체 해법 매칭 (예: 시선 걸림 → 정렬/여백 조정, 인지부하 → 텍스트를 아이콘/색상으로 치환, 단서 불명확 → 버튼 스타일링 강화).

⚠️ 스크립트 상 "훈련법"까지 언급됐으나 이 수집분에는 3개 렌즈까지만 포함됨 — 후속 내용 있으면 추가 수집 필요.

## 구조적 판단기준 (매크로 레벨, 2026-07-14 추가)
위 3대 렌즈는 화면 단위 감각 진단용. 프로덕트 구조 자체가 복잡해질 때는 아래 3가지를 먼저 점검 — 출처 [[reference_toss_product_simplification_cases]]:

1. **화면 자체에 갇히지 말 것**: 컴포넌트 위치·문구 수정으로 안 풀리면 화면을 닫고 "유저가 여기서 하려는 궁극적 행동 가치(Action Value)"를 백지에서 재정의
2. **화려하면서 심플한 건 없다**: 모든 기능을 다 살리면서 깔끔한 레이아웃은 불가능 — 우선순위로 과감히 쳐내고 숨기는 용기
3. **쉬운 길(그냥 예쁘게 그리기)을 의심할 것**: 책상에서 화면만 그리는데 술술 풀리면 유저 무시하고 편한 길 가고 있다는 경고 — VOC·인터뷰·UT로 검증할 것

## 타겟 심리-행동 정합성 체크 (2026-07-14 추가, 포트폴리오 피드백 사례에서)
타겟 페르소나를 정의했다면, **그 타겟의 실제 심리적 동기가 서비스가 요구하는 행동과 일치하는지** 반드시 검증. 불일치 사례: "바빠서 집안일 못 하는 1인가구용 자동 살림루틴 앱" 기획 → 실제 유저 인터뷰 속마음은 "귀찮아서 그냥 다 대신 해줬으면"(게으름) → 근데 서비스는 매일 루틴 커스텀·체크박스 클릭을 요구 → 동기와 요구행동이 정반대. 이런 유저는 가사도우미를 부르지 앱을 안 씀.
- 진단 질문: **"이 타겟은 이 행동을 자발적으로 매일 할 심리적 동기가 있는가, 아니면 이 앱이 요구하는 행동 자체가 타겟의 본능과 충돌하는가?"**
- 올바른 타겟 재정의 예: 위 사례는 게으른 사람이 아니라 "루틴 체킹 자체에서 성취감을 느끼는 살림 매니아"에게 맞는 서비스.

## 실전 검증 규칙 (실전 사례 승격, 2026-07-16)
**법적/메타 레이블(광고·협찬 등)은 매물·상품 정보 텍스트 흐름 "안"에 넣지 말 것.** 텍스트 흐름 안에 두면 인라인(이름 시작점이 밀려 카드 간 열이 깨짐) 또는 독립 배지(붕 떠 보임) 둘 중 하나로 반드시 사고가 난다 — 둘 다 "메타 정보를 콘텐츠 정보와 같은 층위로 취급"한 게 근본 원인.
- 정답 = **썸네일(이미지) 위 코너 오버레이**로 분리. 상태배지가 있다면 반대쪽 코너에 대칭 배치. 이미지 위라 "떠 보이는" 문제가 없고, 텍스트 영역은 순수 상품 정보(가격·이름·유형)만 남아 정렬이 절대 안 깨진다.
- 출처: 고방분양 카드 "광고" 고지 위치를 배지→인라인→코너오버레이 순으로 시행착오 거쳐 확정(사내 판단 사례 2026-07-15 "광고 고지 위치 right-way").

## 실전 검증 규칙 — "레퍼런스 트랜스포즈" (실전 사례 승격, 2026-07-17)
**레퍼런스가 이미 있는 화면(어드민 표·차트·요약·필터)은 새로 디자인하지 말고 트랜스포즈하라.** gobang-admin 매출 모듈에서 "광고 대시보드/상세리포트처럼 하라"는 지시에도 매번 백지에서 새로 발명해 **사용자가 격노할 때까지 5회 왕복**(2단 스택 셀·별도 요약블록·목표대비 분리차트·무지개색·나열형 두 막대) — 전부 레퍼런스를 안 열어보고 발명한 결과. 아이디어 부족이 아니라 프로세스 누락.
- **착수 전 매핑표 필수**: 레퍼런스를 실제로 열어 (열/셀 구성·요약 위치·컨트롤 배치·색 규칙·차트형)을 요소 대 요소로 대조표를 만든다. 신규 발명은 매핑에 대응물이 **없을 때만**.
- **정보밀도**: 요약·컨트롤은 기존 필터/컨트롤 행에 **인라인**(별도 대형 블록 금지). 한 비교(예: 매출 vs 목표)를 **여러 차트로 쪼개지 말 것** — 한 차트에 병합(불릿/2계열).
- **색 = 의미**: 모든 색은 시맨틱(그룹·상태 정체성)을 담는다. **장식용 무지개 팔레트 금지**. 브랜드 단일 키컬러 원칙 유지, 그룹 구분이 필요하면 그룹별 색 "계열(명암 변주)"로 — 카테고리마다 랜덤색은 "긁어온 화면"(사내 판단 사례 반복 경고).
- **데이터형 ↔ 차트형**: 부분-전체·목표진척 = **불릿/오버레이**(채움이 목표선 향해 차오르고, 넘으면 채움이 선 통과)이지 side-by-side 나열 막대가 아니다(나열은 눈이 왕복=렌즈①).
- **3대 렌즈는 사전에**: "5회 왕복 후 격노"는 렌즈를 착수 전 안 돌린 프로세스 실패다. 보여주기 전에 렌즈를 통과시켜라.
- 출처: 사내 판단 사례 2026-07-17 "gobang-admin 매출 차트 5회 왕복 실패".

## 실전 검증 규칙 — 실사용(동적) 검토 의무 (실전 사례 승격, 2026-07-20)
**정적 코드·스크린샷만으로 UX를 판단하지 말 것. 배포본을 실제로 조작해봐야만 나오는 결함군이 따로 있다.** 3대 렌즈(시선흐름·인지부하·어포던스)는 전부 *정지 화면* 진단이라, 아래 4종을 구조적으로 못 본다 — 반드시 별도 패스로 손으로 써본다:
1. **상태 전이·히스토리**: 탭·필터·모달을 여러 번 조작한 뒤 **뒤로가기**를 눌러본다(해시 앵커·pushState가 히스토리를 오염시켜 뒤로가기가 이전 화면 대신 조작 이력을 되짚는 버그는 정독으로 안 보임).
2. **데이터 진실**: "최신순·인기순·추천순" 등 정렬/집계가 **실제 데이터에서 라벨대로 동작하는지** 두 항목을 실측 대조(공고일 A>B인데 B가 위에 오면 정렬 기준이 라벨과 다른 것).
3. **스크롤·뷰포트 지속성**: 길게 스크롤한 뒤 헤더·뒤로가기·필터가 **복귀 가능한지**(사라진 채 안 돌아오면 접근성 붕괴), 스크롤탑 경로가 있는지.
4. **개발자 언어 노출**: 화면 텍스트를 **글자 그대로 읽어** ISO주차(`2026-W29`)·enum 키·raw id·상태코드가 사용자에게 새는지(아래 visual_craft 11번과 짝).
- **경고 신호**: "코드/스크린샷만 보고 합격 줬다" = 이 패스를 건너뛴 것. 실제 UX팀장은 라이브를 손으로 굴려 이 4종을 잡는다.
- 출처: 사내 판단 사례 2026-07-20 "줍줍분양 UX 검토 미스 회고" — 같은 서비스를 정적으로 두 번(07-14·07-15) 평가하고도 히스토리·정렬·스크롤·개발코드 결함 4종을 전부 놓쳤고, 실제 UX팀장이 라이브 조작으로 잡음.

## 실전 검증 규칙 — 페이지 헤더 "전역 vs 로컬" 위계 (실전 사례 승격, 2026-07-20)
**페이지(상단) 헤더는 화면 종류와 무관하게 항상 필요한 전역·상시 기능(뒤로가기 등)의 자리다. 특정 콘텐츠·항목에만 적용되는 로컬 기능을 헤더에 얹으면 위계가 깨진다.** 위 "법적/메타 레이블" 규칙의 일반화 — 레이블뿐 아니라 아래가 전부 헤더에서 내려와야 한다:
- **메타 레이블**(광고·협찬): 해당 항목 단위 정보 → 콘텐츠 영역(이미지 위/제목 옆).
- **적용 범위가 좁은 컨트롤**(㎡/평 단위 토글 등): 그 값이 표기되는 섹션 근처로.
- **화면 전환 액션**(목록↔지도 등): 필터·정렬 컨트롤 무리에 섞으면 "탐색 조건 조정"으로 오인됨 → 전환은 헤더 같은 더 전역적 위치로(필터가 아니라 뷰 전환임을 위계로 표현).
- 진단 질문: **"이 요소가 이 화면 모든 항목에 항상 필요한가(전역), 아니면 특정 항목·값·맥락에만 걸리는가(로컬)?"** 로컬이면 헤더에서 빼라.
- 헤더 자체의 형태(높이·버튼 크기·타이틀 크기/색/굵기)도 화면마다 제각각이면 안 됨 → 공통 헤더로 고정.
- 출처: 사내 판단 사례 2026-07-20 — 상세 헤더에 '광고' 배지·㎡/평 토글이 전역 기능과 나란히 얹혀 있던 것을 두 번 검토하고도 놓침.
