# 비주얼 크래프트 체크리스트 (실무 감수 세션 기반)

출처: 사용자 제공 실무 디자인 컨펌/피드백 영상 스크립트 2건 (2026-07-14 수집). ⚠️증거 등급: 데이터 검증된 원칙(토스 컨퍼런스류)이 아니라 **숙련자의 경험 기반 크래프트 판단**. 절대 법칙이 아니라 체크리스트로 취급할 것.

## 핵심 메타 인사이트
"기본기가 부족하다"는 막연한 지적을 받았을 때, 그 "기본기"의 실체는 아래 체크리스트다 — 신비한 감각이 아니라 구체적으로 점검 가능한 항목들.

## 1. 여백·정렬
- 행간/자간을 **절대 auto로 두지 않는다** — 항상 명시적으로 잡을 것(제목류 120~130%, 본문은 폰트크기의 1.4~1.6배는 기존 원칙과 정합)
- 간격은 4/8배수 스케일: 8·12·16·20·24·32·40
- 좌측정렬 vs 중앙정렬 일관성 유지 — 한 화면 안에서 섞이면 불안정해 보임
- 라운드값이 강한 요소(완전 원형 인풋 등) 안에 텍스트가 있으면 텍스트를 안쪽으로 살짝 들여쓰기(정렬 불안정 방지)

## 2. 타이포그래피 위계
- 본문 12px는 항상 작다는 지적 대상 — 13~16px가 안전 범위(기존 원칙과 정합)
- 굵기: 큰 버튼·타이틀엔 볼드보다 세미볼드가 안정적인 경우 많음 — 볼드는 화면 전체 무게를 올림, 여러 요소에 중복되면 서로 부딪혀 보임
- 타이틀·본문·캡션 3단계 크기 차등을 명확히(기존 위계 원칙과 정합)

## 3. 색상·대비
- 회색 컬러값(#777 등)은 접근성 대비 기준 미달일 수 있음 — 텍스트는 진하게
- 배경이 밝은 이미지 위에 밝은 텍스트를 얹으면 안 보임 — 항상 반대 계열 컬러 또는 딤(dim)/그라디언트로 대비 확보
- 장식적 배경색(회색 카드 배경 등)은 웬만하면 제거 — 답답함의 주요 원인
- 브랜드 컬러는 정말 강조해야 할 곳(선택된 상태 등) 한 곳에만, 나머지는 무채색

## 4. 장식 효과(글래스·블러·섀도우·라인)는 "빼는 게 기본값"
- 글래스모피즘·그라디언트·보더라인·드롭섀도우를 여러 군데 동시에 쓰면 화면이 무거워짐 — 하나 걷어낼 때마다 가독성이 오히려 올라가는 경우가 많음
- 꼭 필요한 경우(텍스트 가독성 확보용 딤 등)만 최소한으로, 그 외엔 제거가 기본
- 사선·회전 등 "기교를 위한 기교"는 이유 없으면 하지 말 것

## 5. 컴포넌트 일관성
- 인풋 필드의 라운드값과 버튼의 라운드값이 다르면(완전원형 vs 각진 라운드) 화면 전체 통일감이 깨짐 — 같은 스케일의 컴포넌트는 라운드·굵기 규칙을 통일
- 아이콘 스타일도 마찬가지로 통일([[reference_ui_ux_core_principles]] 6번과 동일 원칙, 컴포넌트 레벨 적용)

## 6. 정보 그루핑
- 관련 요소(프로필+본문 등) 사이에 다른 UI 요소(인디케이터 등)가 끼어들면 그룹 인지가 깨짐 — 게슈탈트 근접성 원칙의 실전 위반 사례, 그룹 경계를 명확히 할 것

## 7. 이미지·공간감 처리 (실행 기법)
- 배경이 산만한 이미지보다 인물 등 피사체를 부각하고 배경을 정리한 이미지가 집중도 높음
- 포토샵 리터치 기법: 피사체 아웃라인을 따서 배경 위에 살짝 겹치듯 배치(그림자·블러 추가)하면 공간감(원근감) 생성 — 단순 사각형 이미지보다 몰입도 상승
- 과도한 리터치 효과는 오히려 역효과 — 살짝(작은 수치)만 적용

## 8. 인터랙션 디테일
- 필수 정보가 없어도 되는 장식 아이콘(화살표 등)은 텍스트만으로 명확하면 제거 가능
- 탭/버튼 크기는 시각적 무게와 터치 편의성 둘 다 고려해 작지 않게(기존 44pt 터치영역 원칙과 정합)

## 9. 실전 검증 규칙 (실전 사례 승격, 2026-07-16)
- **사진 없는 폴백 커버는 "조용히 비켜줄 배경"이지 정보·그래픽 강조 대상이 아니다.** 정답 = 옅은 틴트(`bg-accent/10`) + 절제된 브랜드 글리프. **텍스트·채도·강조 금지.** — 고방분양에서 이 원칙(텍스트 색면→글리프+캡션→데이터썸네일→텍스트확대→채도타일) 5회 변형을 전부 시도했다가 매번 초기안보다 나빠져 원복한 사례에서 확정(사내 판단 사례 2026-07-15 "폴백 커버 과잉설계 실패").
  - 상세 정보(유형·지역 등)는 이미 카드 본문이 담당 → 썸네일에 중복 얹으면 위계 파괴.
  - "빈 이미지가 허전해 보인다"는 콘텐츠(실사진 부족) 문제이지 디자인 문제가 아니다 — 디자인으로 정보를 밀어넣어 해결하려 들지 말 것. 근본 해결은 운영(실사진 확보).
  - 같은 요소를 3회 이상 고쳐도 사용자가 계속 불만이면 되돌려서 **원점(초기안)과 비교**하라 — 개선 강박이 초기의 절제를 못 보게 만든다.
  - **⚠️교정(2026-07-20, 2차 확정)**: 폴백 색은 "빈 슬롯이냐"가 아니라 **그 매물의 상태**를 따른다. → **활성(접수중·대기중) 매물의 사진 미등록 = 민트(`bg-accent/10`) 유지**(키컬러=활성 신호라 살아있는 매물엔 맞음, 10번), **마감·종료 매물만 중립 회색(`bg-paper-warm`)+저대비 글리프로 낮춤.** ⚠️경로 정직기록: 1차엔 "빈 폴백은 무조건 중립 회색"으로 과교정(활성까지 회색화)했다가 사용자가 *"마감 아닌 활성은 아이콘에 키컬러 쓰라 돼있잖아?"* 로 재지적 → 상태연동으로 최종 확정. **교훈: '빈 상태'와 '비활성 상태'를 한 덩어리로 묶지 말 것** — 활성 매물의 데이터 일부(사진) 부재는 비활성이 아니다. rule 9의 "텍스트·강조 금지·조용히" 정신은 유지, 색만 상태연동.

## 10. 색 = 상태 의미 (키컬러 금지역) — (실전 사례 승격, 2026-07-20)
**색은 브랜드 일관성 축과 별개로 '상태 의미' 축을 가진다. 키컬러(브랜드 주색)는 활성·주요 액션·긍정 피드백·선택 상태 전용이다. 빈·비활성·종료·마감·에러 상태에는 절대 쓰지 말 것.**
- "민트 단일로 통일"(브랜드 일관성)만 보다가 **"이 자리는 어떤 상태를 뜻하는가"**를 놓치면, 빈 썸네일·마감 배지 같은 죽은 자리에 키컬러가 올라가 사용자가 "활성/긍정"으로 오독한다.
- 상태 위계 배색: **활성(접수중/대기중)=흰 배경·키컬러 강조 가능(썸네일 폴백·글리프도 키컬러 OK) / 비활성(마감·품절·종료)=중립 회색(paper-warm·ink-mute), 키컬러·강조색 제거.** 회색은 종료·비활성의 관용색이므로 활성에 회색을 쓰는 것도 반대 방향 오류(활성 매물이 마감처럼 보임).
- ⚠️**"빈값"을 "비활성"과 혼동 금지**: 활성 매물의 사진·일부 데이터 부재는 *빈 슬롯*일 뿐 비활성이 아니다 → 그 자리 색은 매물 상태(활성)를 따라 키컬러 유지. "empty=무조건 중립"으로 과교정하면 살아있는 매물을 마감처럼 죽여버린다(9번 2차 교정 경로 참조).
- 진단 질문: **"이 색이 지금 '활성/주목하라'는 신호를 보내는가? 그렇다면 이 자리는 정말 활성·긍정 상태인가?"**
- 출처: 사내 판단 사례 2026-07-20 — 빈 폴백 썸네일 민트, 활성/마감 카드 배경 무차별 동일, 마감 상태 키컬러 오용 지적. 9번 폴백 규칙의 교정 근거.

## 11. UI에 개발자 언어 노출 금지 — (실전 사례 승격, 2026-07-20)
**사용자 화면에는 사람 언어만. 기계·개발 표기가 새면 안 된다.** ISO 주차 코드(`2026-W29`)·enum 키(`open`/`wait`)·raw id·상태코드·날짜 원본 포맷이 그대로 노출되는지, **화면 텍스트를 글자 그대로 읽어** 점검(위 [[reference_ux_judgment_lenses]] "실사용 검토 의무" 4번과 짝).
- 데이터에 들어있는 값을 **표시만** 하는 코드일수록 위험 — 시트/DB 원본이 `2026-W29`면 그대로 찍힌다. 표시 직전 사람 언어로 변환(`"7월 3째주"`).
- 출처: 사내 판단 사례 2026-07-20 — '이번 주 부동산 이슈' 헤더에 `2026-W29`가 그대로 노출된 것을 두 번 검토하고도 놓침.

## 12. select 필터 기본값은 드롭다운 — 노출형(세그먼트/탭)은 예외다 (실전 사례 승격, 2026-07-28)
**옵션을 고르는 컨트롤을 만들 때 기본값은 드롭다운이다. 세그먼트·탭으로 옵션을 다 펼치는 건 조건을 만족할 때만 쓰는 예외다.** 반대로 습관화돼 있으면(매번 탭·버튼으로 빼면) 사용자가 "지저분하다"고 느낀다 — 실제 반복 지적.
- **드롭다운**: 선택값만 노출, 폭 고정(옵션 20개도 감당), 고르는 데 2클릭. **필터 축이 여러 개인 화면의 기본값.**
- **세그먼트(노출형)**: 전부 노출, 1클릭, 옵션 수만큼 가로 선형 증가라 3~4개가 한계. **예외 조건 = 옵션 3개 이하 + 고정 개수 + 상호배타 + 그 화면에서 가장 자주 토글하는 축, 넷 다 만족할 때만.** 하나라도 어긋나면 드롭다운.
- **탭은 필터가 아니다**: 탭은 "아래 내용 영역이 교체된다"는 관용구 → 필터로 쓰면 화면 전환을 기대하게 만든다(어포던스 위반). 노출형이 필요하면 탭이 아니라 세그먼트 버튼.
- **드롭다운 여러 개 병렬 시 필수**: 닫힌 상태에 **축 이름+선택값 병기**(`일별 ▾` ✕ → `기간 · 일별 ▾` ○). 값만 있으면 똑같은 회색 박스 N개가 되어 라벨을 읽어야 축을 아는 상태(렌즈② 실패)가 된다. 폭은 고정+truncate(레이아웃 흔들림 금지 규칙).
- **화면 종류를 먼저 확정할 것**: 같은 질문에 답이 갈리는 분기점이다. **소비자 서비스**는 "숨긴 기능은 안 쓰인다"(토스 서랍형 달력→탭 전환 시 이용률 4배)가 살아 있어 주요 축 1개는 노출형이 유리할 수 있다. **내부툴·어드민**은 쓰는 사람이 만든 사람이라 발견성 리스크가 사실상 0 → 법칙2(내부툴은 효율 기준)에 따라 **전부 드롭다운이 정답**.
- 출처: 사내 판단 사례 2026-07-28 — 총괄 "항상 UI 만들 때 맨날 탭으로 빼던데" 반복 지적. 이 페르소나가 첫 답에서 세그먼트를 1번 규칙으로 제시해 3회 왕복한 사례.

## 13. 컨트롤 어휘 — 같은 동작은 같은 형태 (실전 사례 승격, 2026-07-30)
**같은 기능이 화면마다 다른 형태로 나오면 그건 취향 문제가 아니라 어휘 부재다.** 색·간격 토큰만 문서화한 상태는 절반이고, 빠진 절반이 **"어떤 동작에 어떤 형태"** 결정표다.
- **형태 수를 세라: 1이어야 한다.** 실측 사고 — '새로고침' 하나가 5곳에서 **4형태**(텍스트만 / 아이콘+텍스트 13px / 아이콘+텍스트 15px / 아이콘만).
- **동작의 종류가 형태를 정한다**: ①쓴다=주색 채움 ②같은 화면에서 연다·더한다=테두리 ③반복·부수=아이콘만+title(**라벨 금지**, 붙이면 ②와 구분 소멸) ④다른 화면으로 간다=텍스트+화살표(**테두리 금지**) ⑤조회 조건=드롭다운(12번).
- **테두리 = 여기서 처리된다 / 화살표 = 여기서 나간다.** 페이지 이동에 버튼 테두리를 주면 모달 여는 버튼과 생김새가 같아져 클릭 전에 결과를 알 수 없다(렌즈③ 위반). 라벨도 목적지를 말해야 한다 — `목표` ✕(이 화면 기능으로 읽힘) → `목표 관리 →` ○.
- **화면에서 버튼·카드 클래스를 손으로 짜지 말 것.** 로컬 `Card`/`Panel`/`ChartCard`를 새로 정의하는 순간 여백·제목 크기·각주 위치가 갈린다(실측 중복 10건).
- 절차·감사 방법은 [[reference_design_system_governance]] — 이 항목은 그 파일의 체크 지점이다.
- 출처: 사내 판단 사례 2026-07-30 "컨트롤 어휘 부재 → 같은 기능 4형태 난립".

## 14. 상태 피드백 — idle·로딩·에러는 항상 시각적으로 구분되어야 한다 (사용자 직접 지시, 2026-08-03)
**"멈췄다"·"불러오는 중이다"·"에러났다"를 사용자가 화면만 보고 구분 못 하면 그 화면은 실패다.** 데이터를 다시 불러오는 모든 시점(필터·기간 변경, 새로고침, 페이지 진입)에 셋 중 하나가 반드시 눈에 보여야 한다. 절대 법칙 — 예외 없이 전 제품 공통.
- **클릭 가능한 요소(버튼 등)** — 눌렀을 때 색 변화·눌림 모션 등 즉각 반응 필수([[reference_ui_ux_core_principles]] 7번과 같은 원칙, 여기서는 "화면마다 있으면 좋다"가 아니라 **예외 없는 필수**로 격상).
- **데이터 재조회 중** — 스피너·스켈레톤·비활성화(dim) 중 최소 하나로 "지금 로딩 중"임을 명시. 카드·표 값이 그냥 멈춰 있으면(바뀌는 기색 없이 방치) 로딩인지 에러인지 사용자가 구분할 방법이 없다.
- **에러** — 로딩이 끝났는데 값이 안 들어왔으면 반드시 별도의 에러 상태(문구·아이콘)로 구분한다. 로딩 스피너가 멈춘 채 방치되거나 빈 화면이 뜨면 "고장났나 아직 도는 중인가"를 사용자가 매번 되묻게 된다(실제 반복 지적 — gobang-admin).
- **디자인팀장 상시 감사 항목**([[reference_design_system_governance]] 규범3에 편입) — 새 화면·데이터 패칭 지점을 만들 때마다 이 세 상태가 다 구현됐는지 확인한다. "나중에 로딩 UI 추가"는 오지 않는다.
- 출처: 총괄 지시, 2026-08-03 — gobang-admin에서 기간 필터 변경 시 재조회 여부를 화면으로 구분할 수 없어 "느려진 건지 멈춘 건지 맨날 헷갈린다"고 지적. 전 제품 공통 원칙으로 명시.

## 서비스마스터 적용 원칙
이 체크리스트는 화면 하나를 볼 때 순서대로 통과시키는 **1차 실무 필터**로 사용 — [[reference_ux_judgment_lenses]]의 3대 렌즈(마이크로 진단)보다 더 실행 레벨. 판단 결과를 줄 때 "어느 항목에서 걸렸는지" 구체적으로 짚을 것.
