# UX 라이팅 시스템 (제품 내부 텍스트 전용)

**범위 경계부터**: UX 라이팅 = 서비스/제품 **내부** 텍스트(버튼·에러·모달·안내문·빈 상태·툴팁 등). **UXUI(디자인팀장) 소관.** 랜딩·광고소재·세일즈 문구 같은 **마케팅/콘텐츠 카피는 별개** — planning(사업기획자)·marketing-lead 소관. 대표 보이스는 비슷하게 갈 수 있어도 톤 통일을 강제하지 않는다(실제 프로덕트팀 정책: "프로덕트 라이팅과 콘텐츠 라이팅은 별개로 가져간다"). 이 경계를 넘어서 랜딩 카피에 이 파일의 원칙(해요체 등)을 그대로 적용하지 말 것 — 다만 원칙5(존중/다크패턴 경계)는 카피 검수 시에도 차용 가능.

## 정의
좋은 문구 = 사용자가 프로덕트를 쓰며 긍정적 경험을 하게 하는 것. 두 방향성이 있고 트레이드오프다 — 서비스마다 무게중심을 먼저 정할 것:
- **효율적 라이팅**: 최소 텍스트로 의미 전달(예: "송금완료: OOO(1,000원)")
- **브랜딩 라이팅**: 개성을 담아 텍스트가 늘어도 자기 목소리를 낸다(예: "OOO님에게 1,000원을 송금했어요")

## 시스템 구조 — 라이팅도 디자인시스템의 부분집합
색·간격 토큰처럼 문구도 토큰화해서 다뤄야 한다([[reference_design_system_governance]] 규범1 "어휘 소유"의 텍스트판). 4단 계층:

**코어밸류 → 보이스톤 → 원칙 → 가이드라인/단어사전**

- **코어밸류**: 프로덕트가 라이팅에서 지향하는 가치. 프로덕트 정체성(보이스)에 가장 가깝다. (예시 템플릿: 명확한·간결한·존중하는·친절한·유용한 — 이 5개를 그대로 복붙하지 말 것, 서비스마다 자기 코어밸류를 먼저 정하고 그걸로 원칙을 파생시킨다.)
- **보이스톤**: 코어밸류로 대표 퍼소나를 정하고 보이스를 부여. 상황별로 다른 톤(문체)을 쓸 수 있되, **기본 문체 하나를 고정**하고 흔들지 않는다. 신뢰를 강조할 서비스는 하십시오체 우선, 극존칭은 지양, 질문형은 "-하시겠습니까?" 류로 통일.
- **원칙**: 코어밸류를 실제 글쓰기 규칙으로 구체화.
- **가이드라인/단어사전**: 맞춤법·숫자표기·영문표기 같은 최소 기준 + "확정단어" 사전(같은 대상을 화면마다 다른 말로 부르지 않기 위함).

**왜 필요한가**: 같은 프로덕트 안에서도 같은 의미를 다른 문구로 쓰거나 띄어쓰기가 일관되지 않으면 그 자체로 나쁜 경험이다. UI를 통일시키듯 문구도 통일시켜야 사용자에게 일관된 경험을 준다 — [[reference_design_system_governance]]가 컴포넌트 어휘에서 말하는 것과 정확히 같은 문제가 텍스트에도 있다.

## 원칙 7개 (범용, 실전 검증된 정책)
1. **올바른 기준으로 쓰기** — 국립국어원 기준 맞춤법·띄어쓰기 일관.
2. **능동태로 쓰기** — 상태를 명료하게.
3. **명확하게 쓰기** — 한 문장에는 하나의 메시지만.
4. **간결하게 쓰기** — 있어도 없어도 메시지가 안 변하는 단어는 삭제.
5. **존중하는 방식으로 쓰기** — 사용자의 선택을 강요하지 않고, 우리 이익 방향으로 유도하지 않는다. (아래 §다크패턴 경계선의 판정 질문 3개로 검증)
6. **이해하기 쉽게 쓰기** — 일상에서 안 쓰는 용어 지양, 같은 대상은 항상 같은 단어(어휘 통일 = governance).
7. **유용하게 쓰기** — 사용자가 다음 화면을 예상할 수 있을 만큼 충분히 설명.

## 실전 검증 규칙 (2026-08-05 마케팅허브 AdPilot 사례에서 승격)
총괄가 "'채널마다 소진 규모가 달라 절대값 비교가 어렵다' 이딴 멘트를 누가 서비스에 쓰냐"고 지적한 사례에서 도출. 원칙2·6의 구체 실패 패턴이자 실행 스펙:
- **시스템 사정 고백 금지** — "~라서 비교가 어렵다"처럼 시스템이 자기 한계를 설명하는 문장은 삭제. 사용자는 "그래서 뭘 보면 되는지"만 필요하다(공급자 언어 → 인간 언어. 3문장 강의를 1문장 판독법으로: "전환당 비용은 낮을수록 좋아요").
- **개발자 어휘 금지어** — 정규화·절대값·원본·스코프 등 코드/주석 말투가 그대로 화면에 새는 것. 원칙6 위반의 최다발 사례.
- **상시 노출은 1줄, 나머지는 툴팁** — 화면에 항상 떠 있는 텍스트는 판독법 한 줄로 축약, 부연설명은 인터랙션 뒤로 숨긴다.
- **해요체 하나로 고정** — 보이스톤에서 정한 문체를 화면마다 다시 정하지 않는다.
- **결론 먼저** — 원인·과정보다 사용자가 할 일/알아야 할 결론을 앞에 둔다.

## 인간화 라이팅 (부록, 토스 사례 — 감정 타이밍이 필요한 순간용)
텍스트가 화면의 30~40%를 차지하는 상황(완료 화면·VOC 응답 등)에서는 위 원칙만으론 부족하다. 상세는 [[reference_simplicity_conference_synthesis]] 부록 참고 — 해피모먼트 증폭("고생 많으셨어요")·VOC 기반 정직한 위로·Losing Pattern(잘되는 패턴보다 "절대 쓰지 말 것" 목록을 먼저 분류해 실무 고민시간 절감).

## 실전 활용 절차 (디자인팀장이 문구를 만질 때)
1. **재사용 우선** — 같은 의미의 문구가 이미 있는지 먼저 찾는다(신규 창작보다 재사용. "레퍼런스 트랜스포즈"[[reference_ux_judgment_lenses]]와 동일 정신).
2. **모호하면 grep으로 실측** — 그 서비스의 확정단어 사전/기존 화면 문구를 실제로 검색해 커버리지를 확인([[reference_design_system_governance]] 규범2 "착수 전 인벤토리 감사"와 동일 절차).
3. **원칙 7개 + 실전 검증 규칙으로 새 문구를 검증**.
4. **개발팀 전달 시 변형 금지** — 시안에 있는 문구를 그대로 구현에 적용, 구현 중 임의 축약·의역 금지(코드가 문구를 재발명하면 다시 흩어진다).

## 다크패턴 경계선 (2026-08-20 `reference_super_expert_4_domains.md`에서 이관, 그 파일 삭제)

유저를 속이는 UI(교묘한 결제 유도·해지 방해)와 **브랜드 신뢰를 지키며 매출을 올리는 '정직한 넛지'** 사이의 선을 문구 단계에서 긋는다. 판정 질문 셋:
1. 이 문구를 **사용자가 나중에 알게 되어도** 화나지 않는가.
2. 유리한 정보와 불리한 정보가 **같은 크기·같은 자리**에 있는가.
3. 되돌리는 길(해지·취소·거절)이 **들어온 길만큼 쉬운가.**

경계군: Decoy(미끼 선택지)·Scarcity(한정재고)·Variable Reward·Sunk Cost(해지 방해)·Internal Trigger — 전환율은 오르지만 넘어가기 쉽다.
⛔ 인위적 마감임박·"놓치면 손해" 압박은 **과장하지 않는 것이 차별점인 제품**(찐정책 등)에서는 금기다.

## 실전 검증 규칙 — 경계 재확인 (같은 뿌리 재발 방지)
UX 라이팅 원칙(해요체·다크패턴 경계 등)을 랜딩·광고 카피 평가에 그대로 들이대지 말 것. 카피의 전략/메시징(포지셔닝·설득력)은 planning 소관이고, UXUI는 제품 내부 문구의 톤·어휘·개발자 언어 노출을 본다. 07-17·07-26·07-29 랜딩 카피 사례가 전부 planning 태그로 판단된 것이 이 경계의 실제 적용 사례다.
