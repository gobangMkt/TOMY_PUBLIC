## 구조·설계
- **단일책임(SRP)**: 함수/컴포넌트는 하나의 책임. 데이터 로직(커스텀 훅)·UI를 분리 → 버그 시 그 부분만 안전 수정. (단 소규모 과분할이 역함정 — 함께 바뀌는 로직은 한 함수에. 쪼개는 기준은 [[reference_architecture_ops]] "분할은 고통이 측정될 때만"과 동일)
- **SLAP(추상화 레벨 통일)**: 한 함수에 고수준 흐름 + 저수준 디테일을 섞지 마라. 세부는 메서드로 추출해 흐름만 보이게. **계산·분기 규칙을 거대 SQL(중첩 CASE·대형 조인·UNION ALL)에 심지 말고 명명된 함수("수수료계산기"·"환전기")로 승격 — 쿼리 속 로직은 리뷰·단위테스트가 안 된다(GAS/Supabase 쿼리가 수십 줄 넘고 도메인 규칙이 끼기 시작하면 발동).** (수준 오르내리면 추출 / 단순 유틸은 예외)
- **부수효과 격리 + 순수함수 지향**: 계산·변환은 순수함수(같은 입력→같은 출력), DB/API/상태변경 같은 부수효과는 함수 경계 한 곳에 몰아 격리. (성능 크리티컬 루프·필수 I/O는 예외)
- **불변성(Immutability)**: 상태를 바꾸지 않는 객체로 추적성·동시성 안전. (도메인 모델·설정값 기본 / 대용량 성능 경로는 신중)
- **Tell, Don't Ask**: 객체 내부 상태를 꺼내 밖에서 판단하지 말고 객체에게 행위를 시켜라(데이터+행위 결합·내부 은닉). (상태 가진 도메인 객체 / 순수 DTO는 불필요)
- **합성 우선**: 진짜 is-a 관계가 아니면 상속 대신 합성. **고객별/설정별 변형도 core에 if 분기를 쌓지 말고 경계에서 구현체를 주입(DI)해 교체 — 표준 코드 불변**(도메인 변형 주입=Strategy로, [[reference_architecture_ops]] 횡단관심사 주입=Decorator과는 다른 축). (변형 축 1~2개면 조건분기가 더 쌈, YAGNI)
- **Props Drilling → 컴포지션/Context**: 3단계 이상 중첩 전달이면 끊어라. (단순 2단계·재사용성 훼손 시엔 그대로 두기)

## 가독성·네이밍
- **의미있는 이름 + 매직넘버 상수화**: `x.p < 1000` → `isInBudget`, `300` → `TOAST_DURATION_MS`. 관용 접두사(`is-`/`handle-`/`fetch-`) 준수, 창의적 작명 자제.
- **위→아래 읽히는 흐름**: 핵심 로직(제출하기)을 상단, 세부 검증(이메일 형식)을 하단. 인지부하 절감.
- **게슈탈트 근접성으로 코드 그룹핑**: 빈 줄로 관련 코드 블록을 시각적으로 묶으면 주석 없이 인지부하 감소. → [[reference_ui_ux_core_principles]] 게슈탈트가 코드에도. (중·장편 함수만 / 짧으면 불필요)
- **분석 이벤트 키는 안정적 id에 묶어라**: 로그·애널리틱스 이벤트 식별자를 버튼 라벨·문구 같은 표시 문자열로 잡지 말고 stable key/상수에 묶어라 — 문구 변경·A/B·다국어에서 표시값이 바뀌면 키가 파편화돼 데이터 시계열이 끊긴다(매직넘버 상수화의 관측 버전). (다국어·문구 A/B 있으면 필수 / 단일 언어·문구 고정 소형앱이면 습관화 권장)
- **비교문 피연산자 순서**: 변하는/조사 대상 값을 왼쪽, 기준/안정값을 오른쪽 (`if (received < expected)`).
- **`get` 접두사는 가벼운 접근자에만**: 무거운 연산엔 `compute`/`calculate`.
- **부정 표현 회피**: `if(debug)` > `if(!debug)`.
- **변수 스코프 최소화**: 첫 사용 직전에 선언, 함수 맨 위 몰아 선언 금지.

## 원칙의 실제 구현 대조
- **⚑ 같은 원칙이 파일마다 다르게 구현돼 있을 수 있다** (2026-08-04 메일허브). "클릭=읽음처리 안 함"이 한 훅엔 반영돼 있고 같은 화면의 다른 패널엔 정반대로 구현돼 있었다 — **주석에 "동일 동작"이라 써 있어도 실제로 그런지 코드로 대조하라.** 한 곳을 고칠 때 같은 원칙을 주장하는 나머지 지점을 grep으로 훑는 게 규범. 한쪽만 고치면 반쪽 수정으로 남아 다음 실패를 만든다.

## 부분 저장 — 좁힌 것을 저장 경로에 넣지 않는다 (2026-08-31 승격, 같은 뿌리 2건)

**⚑⚑ 한 저장 객체를 두 화면이 나눠 쓰면 부분 저장은 반드시 병합이어야 한다.** 전체 교체(`save(obj)`)는 그 객체를 **한 화면이 독점할 때만** 안전하다.
- 실측 사고(블로그-챌린지): `saveCampaign_`이 `saveCampaignDetail_(cid, body.detail||{})`로 detail을 통째 교체하는데, 캠페인 수정 폼은 `guide·notice·eduUrl`(운영 탭에서 따로 저장하는 필드)을 안 보낸다 → **저장 버튼 한 번에 작성가이드가 조용히 사라졌다.** 도입은 두 달 전, 새 필드를 기존 detail 객체에 얹은 커밋이었다.
- 같은 뿌리 사전 차단(AdPilot): 로컬 인사이트 탭이 `list`를 **필터링한 채로** `setList`/`saveReports`까지 하게 짤 뻔했다 — 저장 시 전사·타 묶음 리포트가 로컬스토리지에서 통째로 사라진다. `list`(전체, 저장용)와 `shownList`(필터, 표시용)를 분리해 막았다.
- **규칙: 새 필드를 기존 객체에 얹을 때 그 객체를 쓰는 저장 경로를 전부 센다.** 표시용으로 좁힌 배열은 이름부터 갈라(`shown*`) 저장 함수에 못 들어가게 한다.
- 회귀 그물은 **버그를 일부러 재주입해 실패하는지까지** 확인한다(그 건에서 미러 테스트 8건 중 7건이 재주입 시 실패하는 것을 확인했다).
- ⚠️ **잠재 버그가 있는 화면으로 사용자를 유도하기 전에 그 화면의 쓰기 경로를 먼저 읽는다** — "확인해 보세요"라고 안내한 그 시점이 유실 시점이었을 수 있다.

## 추상화 타이밍
- **3회의 법칙**: 2회 반복은 우연, **3회 이상 + 맥락이 완전히 같을 때만** 공통 함수로 추출. 섣부른 공통화 = 오버엔지니어링 — 나중에 두 화면 요구가 미세하게 갈리면 묶어놓은 코드가 족쇄가 된다. (빈 폴더·선제 추상화를 경계하는 [[reference_engineering_principles]] YAGNI와 같은 결)

## 프론트 렌더링 성능 (클라이언트)
- **고빈도 상태 리렌더 격리**: 고빈도로 바뀌는 상태(실시간 시세·스크롤·커서·라이브 카운터)를 화면 전체를 한 덩어리 상태객체로 상위에서 구독하면 한 필드만 바뀌어도 그 객체를 참조하는 형제 컴포넌트가 전부 리렌더된다 → 소비자엔 각자 필요한 원시값만 좁게 넘기고, 가장 자주 바뀌는 값은 그걸 실제 그리는 최말단 컴포넌트에서 읽어 리렌더 범위를 잎사귀 하나로 가둬라(좁은 selector·memo·leaf 구독). 우리 케이스=지도 뷰포트 onBoundsChanged·무한스크롤 목록. (WebSocket/스트림/프레임 단위 갱신이면 적용, 정적·저빈도엔 조기최적화 YAGNI)
- **연속 시각값은 재조정 건너뛰고 최저 렌더 레이어로**: 크기·위치·투명도처럼 시각 출력에만 영향 주는 연속값(드래그 progress 0~1, 스크롤 오프셋)을 컴포넌트 상태에 바인딩하면 프레임마다 트리 전체가 재조정돼 CPU가 폭발한다 → 상태/재조정 계층을 건너뛰고 가장 싼 렌더 레이어로: 웹=CSS transform/opacity(GPU 컴포지터)·ref 직접 변이+requestAnimationFrame, 매 프레임 setState 금지. (스크롤·드래그·제스처 애니메이션이면 적용, 레이아웃 구조가 바뀌거나 1회성이면 정상 상태갱신)
- **취득 상한 ≠ 렌더 상한**: 목록 길이가 데이터에 비례하면 DOM도 비례한다 — **상한은 데이터를 "가져오는 쪽"이 아니라 "그리는 쪽"에, 뷰포트에 묶어라.** 메일허브는 `DB_LIST_LIMIT = 2000` 옆에 *"상한은 화면 렌더 보호용"*이라 주석까지 달아놓고 그 2000을 DB fetch에만 걸어 1,266행을 전부 그렸다(DOM 2만 노드, 전환마다 최대 1.4초 정지). **"보호용"이라 적힌 상수가 실제로 그걸 보호하는지 대조할 것 — 방어선을 세운 줄 알았는데 세운 자리가 틀린 경우가 있다.** 구현은 라이브러리 없이도 된다: 초기 청크(뷰포트+여유)만 그리고 IntersectionObserver 센티넬로 이어붙이면 행 높이를 가정하지 않아 스크롤바가 안 어긋난다. (수십 행 고정이면 YAGNI)
- **탭·라우트 전환이 언마운트면 그 렌더 비용은 매번 재발생한다**: 무거운 화면을 오가는 구조에선 한 번 연 화면을 `display:none`으로 숨겨 살려두고(방문 전엔 마운트도 안 하는 lazy keep-alive) 재진입을 공짜로 만든다. **대신 "재마운트=재조회"라는 암묵 계약이 깨지니 활성화 시 재조회를 명시적으로 걸고, 그 응답이 직전과 같으면 setState를 생략하라** — 내용이 같아도 새 객체로 갈아끼우면 목록 전체가 다시 그려져 전환마다 수십~수백 ms를 까먹는다(원문 문자열 비교로 충분). 숨긴 화면은 `hidden` 속성도 같이 걸어 접근성 트리·테스트 쿼리에서 빠지게 한다.
- **⚑⚑ 캐시는 층마다 짝이 있어야 한다 — 서버에만 깔면 절반이다** (2026-08-11 고방어드민 실증). 서버 stale-while-revalidate를 잘 깔아 API가 웜 60~80ms였는데도 화면 전환이 7초였다: 라우트를 옮기면 훅이 remount되며 **무조건 재조회**하고, 서버가 빨리 주더라도 **전송(최대 1.5MB)·JSON.parse·파생 재계산은 전환마다 그대로** 낸다. 증상은 "**재방문이 첫 방문보다 느리다**"로 드러난다(재방문 이득이 0) — 이 신호를 보면 클라이언트 캐시 부재를 의심할 것. 클라이언트 캐시는 서버와 **같은 3단 수명**(TTL→stale-while-revalidate→만료)으로 짜고 4가지를 지킨다: ①동시 요청은 in-flight 공유로 왕복 1회 ②`fresh=1`(강제 새로고침) URL은 캐시하지 않되 **받은 값을 보통 URL 키에 심어야** 두 번째 새로고침이 캐시 히트로 무시되지 않는다 ③**응답 원문이 직전과 같으면 통지·setState 생략**(위 keep-alive 항목과 같은 규칙) ④**쓰기 성공 시 무효화는 fetch 래퍼 한 곳에서**(쓰기 경로가 십여 곳이면 호출부 복붙은 반드시 하나가 빠진다 → [[reference_architecture_ops]] 성공시 부수효과). 교체는 `fetch(u).then(r=>r.json())` → `cachedJson(u)` 한 줄이 되게 만들어라(제네릭 기본값을 `any`로 둬 기존 호출부가 타입 주석 없이 옮겨지면 diff가 최소가 되고 그만큼 사고 여지가 준다). (화면 2~3개·응답 몇 KB면 YAGNI)
- **⚑ 접어 둔 것도 렌더 비용은 낸다** (2026-08-21 찐정책). 접힘·탭·모달 뒤의 대량 목록을 "아직 안 보이니 괜찮다"고 넘겼는데, **서버 컴포넌트에서는 그 요소가 이미 만들어져 직렬화된다** — `Collapsible`은 *안 보여줄 뿐* 요소는 존재한다. 실측: 해당없음 679장을 접어 둔 채로 결과 응답이 **40.3초**(5장 쿼리 5.7초 / 상한 30장 적용 후 2.9초). **화면에 안 보이는 대량 목록도 개수 상한을 걸고, 잘랐다는 사실을 화면에 적는다**(헤딩 건수는 전체를 말한다). 위 "취득 상한 ≠ 렌더 상한"의 서버 렌더판이다.
  - ⚠️ **성능 절대값을 dev 수치로 판단하지 말 것**(dev 6.7초 vs prod 0.12초). 단, **상대 비교**(5장 vs 679장)는 dev에서도 유효하다 — 그래서 원인 특정까지는 dev로 하고 수치 보고는 prod로 한다.
- 서버·DB·부하 성능은 [[reference_architecture_ops]].

## 접근성 = 테스트가능성 = 관측가능성 (한 번 투자, 셋 회수)
- 버튼은 `<button>`, 입력엔 `label`, 커스텀 요소엔 `role`/`aria-label`을 제대로 붙이면 ①E2E 셀렉터가 `data-testid` 없이 안정되고 ②"role=button, name='X' 클릭 시 로그" 전역 규칙 하나로 클릭 로깅이 자동화된다. `div`+`onClick` 꼼수는 셋 다 깨뜨리므로 금지. (소규모일수록 테스트·로깅 코드 짤 여력이 없으니 이득이 더 크다)
- **테스트 셀렉터는 시맨틱 우선, testid는 최후**: 프로덕션 코드를 `data-testid`로 오염시키지 말고 `getByRole`/`getByLabel`로 잡아라. testid는 시맨틱으로 도저히 안 될 때만. (Playwright 공식 권장)
