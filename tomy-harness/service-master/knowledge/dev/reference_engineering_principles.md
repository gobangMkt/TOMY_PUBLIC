# 개발 제1원칙 — 효과 × 효율 (dev 방향타)

출처: 개발론 자료(효과/효율·일잘 개발자 3능력·토스포스·GUARDIANS) + TMC25 개발지식 확장편(100년 가는 SDK·평등하게 빠른 웹·작지만 강한 DevOps·비싼 GPU 클러스터·모던 FEP·기술→조직 엔지니어·금융 LLM 내재화·인터널 서비스 전략·오토로그·제로트러스트), 2026-07-15.
큐레이션 등급: 🟡 방향타(메타). 작동 코드 원칙은 [[reference_code_craft]], 실행 상세는 [[reference_architecture_ops]]·[[reference_integration_data]]. 자기계발 훈화·개인 생산성 팁·대기업 조직론은 버리고 판단 원칙만.

## 두 축
- **효과(Effectiveness) = 올바른 것을 만드는가.** 비즈니스 임팩트 큰 문제부터.
- **효율(Efficiency) = 그걸 낭비 없이 빠르게 하는가.**
→ 효율만 높으면 "쓸모없는 걸 빠르게 만드는" 함정. **효과가 먼저.** (성능 지표 개선도 그 자체론 정당화가 아니다 — 새로 무는 고정 인프라비 ÷ 실효 히트율의 실가성비로 판단, 추가 고정비 없는 코드레벨 최적화는 그냥 하라. 성능 판정은 개발자 최신기기+기가와이파이가 아니라 실사용자의 저가기기·3G·음영지역 기준으로 스로틀링 측정)

## 채택 원칙
1. **코드는 수단, 비즈니스 문제가 목적.** "기획서에 있으니 만든다" 금지 → [[reference_toss_service_design_principles]] 근본원인분석과 정합. (무엇을 먼저 고칠지는 발생 '건수'가 아니라 '임팩트/비용' 가중으로 — 전체 12% 건수가 누수 비용의 대부분이었던 사례. 건당 임팩트 균일·추정 불가면 건수로)
2. **적정기술 > 트렌디한 기술.** 서비스 규모·팀 상황에 맞는 가장 빠르고 안정적인 선택. **코드 한 줄 안 짜고 기획·프로세스로 푸는 게 최상수.** (검증 후 최적화 — 비싼 범용 도구로 먼저 빠르게 출시해 시장 검증 → 살아남은 승자만 저비용·전용으로 전환, 미검증에 인프라·정제 선투자 금지)
3. **YAGNI = 오버엔지니어링 경계.** 안 올 미래 위한 과설계 금지 → [[reference_simplicity_conference_synthesis]]. **("전부 싹 다 개선해" 같은 전면 지시도 감사자 본인이 매긴 우선순위(🔴/🟠/🟡)를 무시하고 기계적으로 다 하라는 뜻이 아니다 — 🟡로 판정한 근거를 밝히고 스킵하는 게 지시 이행이다. 2026-08-04 메일허브.)**
4. **바퀴 재발명 금지.** 검증된 OSS·프레임워크·SaaS 활용, 비핵심을 직접 만들지 마라.
5. **미래 비용으로 보는 코드 품질.** 가독성·유지보수성은 미래 수정비용 절감(당장 속도 vs 미래 비용 트레이드오프). (리팩토링의 값싼 마지막 창 — 시스템이 온전하고 만든 사람·맥락이 남아있을 때가 선제 리팩터 적기. 지식 증발 후 터지는 장애는 회복 불가 비용. 곧 폐기·저위험이면 방치도 합리)
6. **자동화로 human error 원천차단.** 반복작업(테스트·빌드·배포 CI/CD)은 최고 효율 투자, TDD로 디버깅 선지불. 느린 프로세스는 인력 추가 말고 임계경로(가장 긴 수작업 사슬)를 자동화로 잘라라(브룩스 법칙 — 사람 더하면 소통비용이 먹어 더 늦어진다). **(단 1회성·저빈도 작업은 수동이 싸다 — 자동화도 YAGNI, 파이프라인 구축비 > 절감이면 하지 마라)**
7. **비개발자 눈높이 설명.** 기술 제약·원리를 전문용어 없이 (비개발자에게 설명할 때 직접 적용).
8. **도입률이 성공지표 (Adoption over Completion).** 내부 도구·공유 모듈·라이브러리 등 '남이(다른 팀·미래의 나) 써야 가치 나는' 산출물은 완성도가 아니라 실제 도입이 성공 지표다 — 성능 3배·테스트 100%·문서 10p여도 아무도 안 쓰면 0점. 혼자여도 만든 컴포넌트·유틸이 재사용 0이면 실패로 계측. (1회용 버리는 스크립트엔 과함)
9. **통제 불가 런타임 = 방어를 배포 전으로.** 내 코드가 남의 런타임·코드베이스 안에서 도는 순간(임베드 스크립트·배포 라이브러리·공유 GAS·위젯·npm) 사후 핫픽스가 불가능하다 → 모든 방어(입력검증·과부하방지·계약불변)를 배포 전에 끝내라. (배포·롤백을 100% 통제하는 자체 앱/서버면 과방어는 오버) → [[reference_integration_data]] 인바운드 신뢰경계와 형제.
10. **핵심 외부의존은 통제권을 설계.** 단일 외부(LLM·PG·클라우드)에 크리티컬 경로를 통째로 걸면 그 장애=내 전면 장애·비용폭증·락인(ChatGPT 장애로 사내 AI 마비 사례). **소규모 디폴트=매출/핵심 UX 경로면 어댑터 seam만 얇게 두고 하드 비용상한(BQ빌더 ₩900식)까지, 폴백·캐시응답·기능축소 구현은 실제 장애 겪은 뒤에(YAGNI).** 저위험 부가기능까지 추상화는 오버 → 배선은 [[reference_integration_data]].

## 보안 = 엔지니어링 (DevSecOps)
**(a) 원칙 — 왜:**
- **Attack Surface 인지**: 내가 짠 코드·인프라 설정 전부가 공격 포인트.
- **자산 범위 확장**: 물리서버·사내 PC뿐 아니라 VM·소스코드·고객데이터 전체를 통제 대상으로.
- **Speed(개발) × Safety(보안) 균형**: 한쪽 무시하면 갈등, 보안은 방해가 아니라 안전한 비즈니스를 위한 활동.

**(b) 실행 규칙 — 어떻게:**
- **다층 방어 / 침해 전제**: 한 겹(인증·경계)이 뚫려도 다음 겹(서버측 재검증·DB 권한정책·역할체크)이 무조건 막게 겹겹이. 실질 = 클라 검증만 믿지 말고 서버+DB 정책 2겹(금전·인증·개인정보 필수). ("경계 안이니 신뢰" 가정을 버림 = 제로트러스트. 유출돼도 무해한 공개데이터·버리는 내부툴이면 과함)
- **PII 싱크 마스킹**: PII(계좌·잔액·연락처)를 로그·분석·에러리포트로 내보낼 때 각 호출부가 기억해 가리게 말고 로깅 래퍼/전송 경계 한 곳에서 강제 마스킹(분산 방식은 반드시 누락) → [[reference_architecture_ops]] 횡단관심사 중앙화의 보안 인스턴스. (민감정보 안 싣는 순수 시스템 로그면 과함)
- **시크릿 런타임 주입**: 시크릿(DB비번·API키·HMAC키)은 소스·설정파일·로그·클라 번들에 평문 금지 → 시크릿 스토어(Vercel 암호화 env·KMS)에 두고 사용 시점 주입, 커밋되는 건 값 없는 키 목록(.env.example)뿐. → [[reference_architecture_ops]] Fail Fast(필수 env 부팅 검증)와 짝.
> 보안 실행규칙이 더 쌓이면 `reference_dev_security.md` 분리 검토(현재 dev 6파일이라 한 섹션 유지).

## 실전 사례 (원칙의 증거) — 토스포스
- **MVP 2주 검증**: 완벽제품 몇 달 X → 핵심경험만 2주 → 현장 러닝 후 본개발.
- **현장 즉석개발**: 매장 특수운영 예외를 현장서 해커톤식 해결. **"답은 현장에 있다."**
- **오버엔지니어링 실증**: 화려한 프로모션 인터랙션 = 유저가 "광고"로 무시 → 단순 구조로. **만드는 쪽 멋짐 ≠ 유저 인지** → [[reference_uxui_visual_craft_checklist]] 다크패턴 경계. (AI 파이프라인도 현장 암묵지 관찰에서 역설계 = [[reference_llm_rag]] 현장리서치 적용판)

## ★관통 메타원칙 (노션 개발지식 40편에서 반복 확인)
- **좋은 관행은 사람 의지에 맡기지 말고 시스템으로 강제하라.** 문서·테스트·린트·보안·권한은 "권고"로는 반드시 무너진다 → 반복 위반이 관측되면 게이트(CI Fail)·가드레일(기본값·부팅검사)로 승격 → [[reference_architecture_ops]] 가드레일>게이트. 문서·예제도 코드와 한 생명주기(복붙 즉시 실행되는 예제만, 미갱신은 "완료 아님"). 반복되는 수용/거절·공통화 결정은 주관 몸빵 대신 정량 rubric으로 — **단 반복 협업 결정(외주/제휴 수용·팀원 평가·공통화 스코프)일 때만, 솔로 1회 판단엔 몸빵이 쌈.**
- **고친 버그는 회귀 테스트로 잠가라.** 수정 시 그 버그를 재현하는 테스트(사용자 동작 시나리오)를 함께 남긴다. 수정만 하면 리팩터·업글 때 재발 — 같은 버그 2번+ 재보고 시 3번째 추측패치 대신 이 잠금부터.
- **문제는 운영 볼륨/부하에서 드러난다** (성능=옵티마이저 배신·접근성·정합성). 성능 정본=이 축, 구체는 [[reference_integration_data]]·[[reference_architecture_ops]].
  - **⚑ 볼륨 전제가 바뀌는 "사건"을 성능 재검토 트리거로 등록하라** (2026-08-11 메일허브 실증). 위 원칙은 *언제 다시 보는가*가 비어 있었다. 백필 완주·대량 마이그레이션·유저 유입 급증은 예측 불가가 아니라 **로그에 날짜가 찍히는 사건**이다 — 그날 화면을 다시 열어 재라. 메일허브는 8/4 감사일 DB 1통 → 8/7 백필 완주로 +1,260통, 그 사건에 트리거가 0이라 4일 뒤 사용자 신고로 발견됐다. 그 사이 8/10에 같은 앱을 두 번 만지고도 못 봤다(만진 화면만 봐서). **YAGNI로 미룬 결정에는 반드시 "언제 다시 볼지"를 같이 적어라 — 트리거 없는 YAGNI는 그냥 방치다.**
  - **⚑ 코드 리딩 감사와 계측 감사는 잡는 병목의 종류가 다르다** (2026-08-11). `useMemo` 누락은 읽으면 보이지만 "DOM 2만 노드"는 아무리 읽어도 안 보인다. Read/Grep만으로 끝낸 성능 감사는 절반만 본 것 — **"성능"이 의뢰에 들어 있으면 브라우저/프로파일러를 반드시 띄운다.** (순수 서버 로직이면 부하 스크립트로 대체)
  - **⚑⚑ 그보다 먼저 — 성능 진단 0번은 "지금 무엇이 어떤 모드로 돌고 있나"다** (2026-08-11 고방어드민 실증, 같은 날 두 번째 성능 신고). 체감 지연 1위가 **운영을 개발 모드(`next dev`)로 띄워 둔 것**이었다: 같은 코드로 항목 전환 dev 7,361ms vs prod 159ms(46배), 클릭 반응 2~3초 vs 0.05~0.11초. 이 낭비는 **코드 리딩으로도 프로파일링으로도 안 잡힌다**(코드는 정상이고 프로파일은 "dev 런타임이 느리다"만 말한다) — 잡으려면 **포트 리슨 PID·커맨드라인·빌드 모드를 직접 확인**해야 한다. 그래서 순서는 **①실행 모드 확인 → ②계측 → ③코드**. 같은 부류(자릿수가 큰 '설정이 개발용으로 남음'): 디버그 로깅 상시 on, 소스맵·인스트루먼트 부착, 캐시 비활성 플래그, 압축 없는 응답, 로컬 DB에 인덱스 없음.
  - **⚑⚑ 성능은 기능의 완료 조건에 넣어라 — 아니면 화면 수에 비례해 조용히 느려진다** (같은 사건의 근본 원인이자 "왜 자꾸 느리게 개발하나"의 답). 어드민은 화면을 붙일 때마다 데이터 훅을 새로 만들어 **각자 fetch**하게 뒀다. 서버 캐시는 이미 잘 깔려 있었는데 클라이언트 짝이 없어서, 한 원장(`/api/revenue`)을 8개 화면이 각자 매번 받는 구조가 됐다. **개별 커밋은 전부 정상이고 테스트도 전부 통과였다 — 느려졌다는 신호가 어디에도 없었다.** 기능 단위 리뷰는 "이 화면이 동작하나"만 보고 "화면이 20개가 되면 어떻게 되나"를 못 본다 → ①공용 취득/렌더 계약을 만들고 새 화면이 그걸 경유하게 **가드레일로 강제** ②"화면·항목·열 수가 N배 늘어난 시점"을 볼륨 사건과 동급의 **재검토 트리거**로 등록 ③완료 보고에 기능 동작만이 아니라 **그 화면의 전환·정착 실측치**를 함께 남긴다(숫자가 남으면 다음 사람이 회귀를 본다).
- **Blameless Post-Mortem**: 장애 회고는 "누가"가 아니라 "무엇이 이 실수를 가능하게 했나(시스템)". (조직/피플 상세는 org-management-agent 소관)
