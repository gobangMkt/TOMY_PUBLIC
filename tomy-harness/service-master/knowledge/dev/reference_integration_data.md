# 외부연동 · 데이터 정합 (dev — 실무 직결)

출처: 토스 TMC25 "개발지식" 결제·OpenAPI·분산트랜잭션·대용량·100년 SDK·정산 세션 서브에이전트 판별(2026-07-15). 규모 무관 원칙만 환원(Kafka·오라클·Data Mesh는 폐기).
큐레이션 등급: 🟠 대형서비스(토스페이먼츠) 실적용. **우리 신청허브·알림톡·결제·웹훅 체인에 즉시 적용** — HMAC 버그·이중발송방지가 여기 정식화됨.

## 외부 호출 (결제·발송·웹훅)
- **인바운드 신뢰 경계**: 들어오는 건 안 믿는다. 받는 웹훅=서명(HMAC) 검증, 결제/인증 콜백=nonce+타임스탬프로 replay 차단, 공개 엔드포인트=rate limit. **+ 입력 shape은 정적 타입(TS)이 런타임에 증발하니, 신뢰경계 최외곽(API route·GAS entry·폼·LLM tool input)에 런타임 스키마(Zod 등)를 보초로 세워 core 실행 전 fail-fast.** (돈·인증·외부발송 필수 — 알림톡 HMAC 이력과 정합 / 검증된 내부 신뢰코드 간 호출엔 불필요)
- **재시도 가능한 외부 호출엔 멱등키(Idempotency Key)**: 두 번 실행되면 안 되는 호출(결제·발송)은 고유키로 중복 방어. (우리 '이중발송방지 타임스탬프'의 정식화)
- **외부 비동기 전송은 실패 전제 설계**: 지수 백오프 재시도 + 실패 가시화 + 수동 재처리 수단, 결과는 3진 저장(아래 '외부 체인 트랜잭션'). 내 통제 밖 서버로 나가는 모든 비동기(웹훅·알림톡·이메일).
- **종단간 타임아웃은 계단식**: 앞단(게이트웨이) 타임아웃 ≥ 뒷단(결제승인) 최대 처리시간. 반대면 "돈은 빠졌는데 주문 실패"라는 최악의 불일치(신청허브→GAS→SOLAPI/토스 체인 실발생 가능). (외부 홉 없는 단일 동기호출엔 불필요)
- **외부 API 한도에 맞춘 Rate Limiter**: 내가 빨라도 외부(SOLAPI·카카오·토스)가 못 받으면 상대 처리한도에 맞춰 내 쪽에서 스로틀. (외부 한도 여유·호출 드물면 생략)
- **임베드 계측 Self-DDoS 방지**: 남이 호출하는 함수·SDK·위젯에 네트워크·로깅 사이드이펙트를 심으면 소비자가 루프로 호출해 자폭 트래픽이 된다 → debounce·batch·sampling·자체 rate-limit로 호출빈도와 분리('남이 트리거하는 내 사이드이펙트' 스로틀, VoC·통계 API 등). (순수 계산 함수엔 불필요)

## 외부 체인 트랜잭션 · 실패 보정
한 행동이 여러 외부 홉을 건널 때(제출→API→GAS→시트→알림톡)의 정합성 설계. 결정 흐름:
- **재시도 vs 보상을 비즈니스 가치로 선택**: '장애=무조건 롤백'(Saga)이 아니라, 미결 건을 (a)멱등 재시도로 성공 수렴 (b)보상취소로 실패 수렴 중 이득 큰 방향을 택하라. 대부분 이미 성공·1건만 지연이면 재시도가 전부 롤백보다 UX·매출 우위. (부수효과 하나면 그냥 재시도/실패로 충분)
- **보정은 되돌리기 쉬운 것부터 (3척도)**: 내부 가역 단계(검증·예약·기록)를 먼저 다 성공시키고 취소 어려운 액션(카드승인·타계좌 차감·외부발송)을 맨 마지막에 → 실패해도 로컬 롤백으로 끝. 순서 판단=①사용자 체감가치(현금>포인트) ②보상 난이도(가산 易·차감/취소 難) ③통제 가용성(내부 易·은행/외부 難). (부수효과 전부 로컬·가역이면 순서 불필요)
- **결과는 3진(UNKNOWN 1급) + reconciler**: 통제 밖 호출은 타임아웃/유실 때 '성공인지 실패인지 모름'이 필연 → status에 SUCCESS·FAIL만 두지 말고 UNKNOWN/PENDING을 1급으로 저장, 분단위 스케줄러(크론·GAS)가 재조회·재보정해 최종적 일관성. 타임아웃을 곧바로 실패로 단정하면 이중결제·머니 유실. (부수효과 전부 로컬·가역이면 생략)
- **트랜잭셔널 아웃박스**: 'DB 먼저 쓰고 외부 호출' 사이 크래시 시 발송·이벤트가 조용히 유실 → 상태변경과 '보낼 일(outbox 행)'을 같은 트랜잭션에 커밋하고 별도 워커(cron/GAS)가 드레인·재시도. (카프카 불필요, Supabase outbox 테이블+워커면 충분 / 유실돼도 무해한 통지엔 과함)
- **실패 단위 축소**: N건을 하나의 대형 트랜잭션으로 묶으면 1건 실패에 전체 롤백 → 커밋 단위를 잘게 쪼개 실패한 행만 타깃 재처리. (배치·마이그레이션·대량 발송 건수 커질수록 이득)

## 데이터 정합
- **금전 데이터는 append-only, Update 금지**: 결제 취소는 기존 행 수정 말고 취소 레코드를 Insert. 돈·포인트·재고처럼 분쟁·정산 추적(audit) 데이터는 덮어쓰지 마라(GAS 시트=행 수정 대신 행 추가). **+ 집계·통계 결과만 적재하면 오차 시 원천 역추적 불가 → 개별 원천 건을 남기고, 계산에 쓴 수수료율·요금제를 '그 시점 스냅샷'으로 함께 저장(설정 바뀌어도 과거 재현).** → [[reference_code_craft]] 불변성의 구체 적용판.
- **원자 데이터 모델 + 상위 조합 계층**: 테이블/시트는 한 개념(한 행위·엔티티)만 담는 원자 계층으로, 지표·요약은 원자들을 조합해 파생하라 — 여러 개념 섞인 와이드 테이블은 이해·재사용이 무너진다([[reference_code_craft]] SRP의 스키마 적용판). (3~4컬럼 사소한 데이터는 YAGNI, 개념 여럿 섞이고 집계·재사용 수요 있을 때만)
- **성능은 운영 데이터 볼륨에서 드러난다**: 소량 테스트 땐 인덱스 타던 쿼리가 데이터가 쌓이면 옵티마이저가 풀스캔으로 배신한다. 계속 쌓일 쿼리는 실제 볼륨·인덱스로 검증. → 정본 [[reference_engineering_principles]] "운영 볼륨에서 드러난다", DB 성능 튜닝 상세는 [[reference_architecture_ops]].

## 계약 · 연동 인터페이스
- **인터페이스 일관성**: 같은 리소스는 어디서 나오든(API 응답·웹훅) 동일 스키마. **통합 표면을 raw 프로토콜(postMessage·webhook·원시 fetch/JSON)로 노출하지 말고 얇은 타입드 클라이언트(SDK)로 감싸 `x.add()`·`open()` 같은 단순 함수 호출만 남겨라** — 같은 원시 호출/파싱을 2곳 이상 손으로 짜기 시작할 때. (노출 채널 하나뿐이면 자명)
- **공개 계약은 무파괴 진화**: 남이 의존하는 인터페이스는 파괴적 변경 금지, 버전(헤더/경로)으로 신·구 병행. **레거시 교체는 Strangler — 소비자 코드 그대로 두고 레거시의 호출 경로만 프록시로 신 시스템을 향하게 바꿔, 흡수 후 점진 철거(zero-impact).** (외부/타팀 의존 계약일 때만 / 소비자 나 하나면 직접 교체)
- **계약을 구현과 분리**: 2개 이상 앱/레포/외부가 내 인터페이스에 의존하면 소비자가 붙잡는 건 계약(타입·에러코드·제약·mock)이지 구현이 아니다. (소규모=프론트-백 공용 타입 파일/폴더로 단일화, npm 버전배포는 외부 소비자가 실제로 생길 때만 / 소비자 하나뿐인 내부 모듈이면 과분리)
- **외부 연동 차이는 어댑터로 격리**: 외부 시스템(결제·알림·ERP·CRM) 규격 차이를 if-else로 비즈니스 코드에 흩뿌리지 말고 공통 인터페이스 뒤 어댑터로 각 연동을 격리(새 연동=어댑터 1개 추가, 코어 무수정). (같은 종류 외부연동이 2개↑ 될 때 = [[reference_code_craft]] 3회의 법칙 / 연동 1개뿐이면 2번째 등장 때)
- **크로스-바운더리 상관ID**: 한 행동이 여러 경계를 비동기로 건널 때 최외곽에서 상관ID(주문번호·전화번호·PR#) 하나를 발급해 모든 홉에 전파 → '보냈지만 유실'을 end-to-end 재구성·탐지. 자체 헤더 못 심는 연동(결제 콜백·비동기 리포트)은 상대가 계약상 echo하는 유니크 필드를 correlation key로 삼아 요청 시 짧은 TTL 캐시에 컨텍스트 저장→콜백 때 역조회. (단일 프로세스 완결 흐름엔 불필요)
- **테스트/샌드박스 = 같은 코드 + 프로파일**: 별도 테스트 코드베이스를 만들면 갈라져 신뢰도 붕괴, 결제·발송 같은 외부 통신만 모킹. (외부통신 없는 순수 로직 테스트엔 모킹 자체 불필요)
- **셀프서비스 디버깅 + 복구 루프**: 외부 연동자에게 자기 요청/응답/에러 로그를 노출해 자가해결(같은 문의 2회+면 응대 대신 도구·메시지 개선에 투자). 발급한 키/웹훅 소비자가 위협(폭주·어뷰징)이 되면 전면 영구차단이 아니라 ①키 단위 즉시 격리 ②무엇이 문제·어떻게 고치는지 통지 ③고치면 재검증 후 재연결('적대' 아닌 '고장난 파트너').
