# 릴스 기획·평가 (팀 배포판)

Claude가 이 스킬의 기준을 읽고 직접 판단한다.
- 릴스 판단 기준(이하 KB): `~/.claude/shortform-review/knowledge/shortform/`. 처음 한 번 이 스킬 폴더의 `knowledge/shortform/`(씨앗)를 복사해 만든 **내 사본**이다. 이 사본은 내 것이라 자유롭게 고치고 키운다
- 마케팅 판단(훅·카피·퍼널·타겟팅): **사용자의 마케팅 어시스턴트**. 이 스킬에 든 `marketing-lead/`는 그 어시스턴트에 흡수시키는 지식 묶음이다.
- 사용자 설정: `~/.claude/shortform-review/config.md`
- 사용자 레퍼런스: `~/.claude/shortform-review/references/{주제}/` (사용자가 모은 릴스 분석과 주제별 정리)

`~/.claude/shortform-review/`는 스킬을 업데이트해도 지워지지 않는다. 쌓이는 곳은 세 군데다.
| 무엇 | 어디 | 누가 쌓나 |
|---|---|---|
| 릴스 판단 기준(템플릿·엣지 등) | KB | 사용자와 Claude가 함께. 평가·기획·레퍼런스에서 확인된 것을 그때그때 고쳐 쓴다 |
| 사용자 주제별 레퍼런스 | `~/.claude/shortform-review/references/` | 사용자가 레퍼런스를 줄 때마다 |
| 마케팅 지식 | 사용자 마케팅 어시스턴트 | 흡수 + 어시스턴트 자체 성장 |

## 0. 처음 한 번: 설치 마무리
### 0-1. 도구 설치 (Windows)
사용자에게 묻지 말고 없으면 설치한다.
1. 확인: `yt-dlp --version`, `ffmpeg -version`, `python -c "import faster_whisper"`
2. 없으면:
   - `winget install --accept-source-agreements --accept-package-agreements yt-dlp.yt-dlp`
   - `winget install --accept-source-agreements --accept-package-agreements Gyan.FFmpeg`
   - `python -m pip install faster-whisper numpy` (python이 없으면 `winget install Python.Python.3.12` 후 진행)
3. 설치 직후 PATH가 안 잡혀도 `scripts/prep.sh`는 winget 설치 경로를 직접 찾는다.
4. 받아쓰기 모델은 첫 실행 때 내려받는다(약 2분 반).

### 0-2. 마케팅 어시스턴트 지정
`~/.claude/shortform-review/config.md`가 없으면 사용자에게 묻는다.
> 마케팅 판단을 맡을 본인 마케팅 어시스턴트가 어디 있나요? 폴더 경로(예: `D:\work\marketing-assistant`)나 Claude 스킬 이름을 알려주세요. 이 스킬에 든 마케팅리드 지식을 그 어시스턴트에 더해서 키웁니다.

- 스킬 이름을 받으면 `~/.claude/skills/{이름}` 또는 현재 프로젝트 `.claude/skills/{이름}`, `.agents/skills/{이름}`에서 실제 폴더를 찾아 경로로 바꾼다. 못 찾으면 다시 묻는다.
- 어시스턴트가 없다고 하면 `~/.claude/marketing-assistant/`를 새로 만들고(입구 파일 `README.md` 한 장) 그곳을 쓴다.
- 받은 내용을 `config.md`에 적는다:
```
# shortform-review 설정
- 마케팅 어시스턴트: {절대 경로}
- 입구 파일: {SKILL.md / CLAUDE.md / README.md 중 실제 파일}
- 흡수한 마케팅리드 지식 버전: 없음
```
- "마케팅 어시스턴트 다시 지정해줘"라고 하면 이 단계를 다시 한다.

### 0-3. 마케팅리드 지식 흡수
`marketing-lead/INGEST.md` 절차대로 어시스턴트에 지식을 더한다. 기존 내용은 지우거나 고치지 않고 덧붙이기만 한다. 끝나면 결과를 보고한다.

### 0-4. 내 기준 사본 만들기
`~/.claude/shortform-review/knowledge/shortform/`가 없으면 이 스킬 폴더의 `knowledge/shortform/` 전체를 그 자리로 복사한다(사용자에게 묻지 않는다). 이후 모든 릴스 판단은 사본(KB)만 읽고 쓴다. 스킬을 다시 설치·업데이트해도 사본은 덮어쓰지 않는다.

## 1. 매번 시작할 때
1. `config.md`를 읽는다. 없으면 0-2부터. KB가 없으면 0-4.
2. `marketing-lead/MANIFEST.md`의 버전이 `config.md`의 "흡수한 버전"과 다르면, 바뀐 파일만 `INGEST.md` 절차로 흡수한 뒤 본 작업으로 간다.

## 2. 릴스 읽기
1. 링크에서 릴스 ID를 뽑는다(`instagram.com/reel/{ID}/`).
2. `bash scripts/prep.sh <임시폴더> <ID> [<ID> ...]`. 릴스마다 `meta.txt`(캡션·좋아요·댓글·게시일·댓글 앞 15개), `sheet.jpg`(장면 18칸), `hook_*.jpg`(처음 3초), `transcript.txt`(음성)가 생긴다. 임시폴더는 작업 폴더 밖 임시 경로.
3. 메타·받아쓰기를 읽고 이미지를 직접 보고 시간순 구간표(구간 초 / 화면 / 자막·음성 / 역할)를 만든다. 영상 전체를 본다.
4. 조회수·팔로워 수는 메타에 없다. 사용자가 알려주거나 로그인된 브라우저로 그 계정 프로필의 릴스 탭에서 읽는다. 못 읽으면 "미확인".
5. 다운로드 실패(연령 제한·비공개)면 사유를 말하고 화면 캡처나 영상 파일을 달라고 한다. 우회하지 않는다.
6. 영상은 분석에만 쓰고 끝나면 임시폴더째 지운다. 재게시하지 않는다.

## 3. 레퍼런스 수집·정리
"레퍼런스로 쌓아줘" + 릴스 링크(여러 개 가능)가 오면 저장한다. 평가와 달리 기록으로 남긴다.
1. **주제를 정한다.** 무엇을 마케팅하려고 모으는지 한 단어로(예: `청년주택`, `원룸청소`). 말하지 않았으면 한 번 묻는다. 폴더: `~/.claude/shortform-review/references/{주제}/`
2. 2장 절차로 읽고, KB의 `record-template.md` 형식으로 `references/{주제}/reels/{게시일}_{계정}_{ID}.md`에 저장한다. 같은 ID가 있으면 새로 만들지 않고 조회수·팔로워만 고친다.
3. 목적·템플릿·엣지는 KB로 판정한다. KB 템플릿에 없는 구성이면 "새 구성"으로 적는다.
4. **주제 정리 파일 `references/{주제}/정리.md`를 갱신한다.** 아래 형식을 지키고, 레퍼런스가 늘 때마다 고쳐 쓴다(덧붙이기만 하지 않는다).
```
# {주제} 릴스 레퍼런스 정리
## 무엇을 마케팅하나 (한두 줄)
## 레퍼런스 목록
| 게시일 | 계정 | 목적 | 템플릿 | 조회수 / 팔로워 | 한 줄 요약 |
## 이 주제에서 먹힌 구성 (목적별)
- 바이럴 / 유입 / 구독: 반복된 구간 구성, 근거 레퍼런스, 성과
## 이 주제에서 반복된 엣지·새 구성
## 안 먹힌 것 (조회수가 팔로워 대비 낮은 레퍼런스와 그 차이)
## 기획에 바로 쓸 점 (3~5개)
```
5. 보고: 저장한 건수, 정리 파일에서 바뀐 부분, 아직 부족한 것(예: "유입 목적 레퍼런스 0건", "조회수 미확인 4건").
6. KB에 없는 방식이 나오면 `edges.md`의 `## 새 후보`에 가설로 적고, 서로 다른 계정 3곳 이상에서 반복되면 패턴으로 올린다(아래 "기준 키우기").

**좋은 레퍼런스 고르는 법 (사용자가 물으면 안내):** 같은 업종·타깃 계정의 프로필 릴스 탭에서 조회수가 팔로워보다 크게 나온 것 위주로 고르고, 같은 계정에서 안 된 것도 1~2개 섞는다. 잘 된 것과 안 된 것을 나란히 봐야 차이가 보인다. 주제당 5~10개면 기획에 쓸 만해진다.

## 4. 무엇을 읽고 누가 판단하나
| 판단 | 근거 |
|---|---|
| 그 주제에서 실제로 먹힌 구성 | `~/.claude/shortform-review/references/{주제}/정리.md` (있으면 가장 먼저) |
| 목적(바이럴·유입·구독), 템플릿 구간, 기본기, 엣지, 버릴 것 | KB (`review.md` → `목적.md` → `README.md` → `purposes/*.md` → `basics.md`·`expired.md`·`edges.md`) |
| 훅 문장, 카피, 심리 트리거, 퍼널 단계, 타겟·포지션, 콘텐츠 유형, 다크패턴 | **마케팅 어시스턴트.** 입구 파일의 상황별 안내대로 해당 지식을 읽고 근거를 댄다 |
| 트렌드 질문 | `edges.md` 사례 게시일과 `reels/` 게시일을 시기별로 비교 |

마케팅 판단을 감으로 쓰지 않는다. 어시스턴트의 어느 파일 어느 절인지 근거를 붙인다.

## 5. 평가 (팀원·서포터즈 릴스)
KB의 `review.md` 순서: 목적 → 템플릿 → 기본기 → 버릴 것 → 엣지 → 성과.
- 고칠 점은 구간(초)을 짚고 어떻게 바꿀지까지. 근거는 템플릿 구간이나 마케팅 어시스턴트 지식.
- 조회수 절대값으로 비교하지 않고 팔로워 대비 배수로 본다.
- 출력은 `review.md`의 "평가 출력 형식". 여러 건이면 끝에 공통 문제를 한 표로.

## 6. 기획
1. 무엇을 마케팅하는지, 목적(바이럴·유입·구독), 올릴 계정을 확인한다. 빠진 것만 묻는다.
2. **그 주제의 레퍼런스(`references/{주제}/정리.md`)가 있으면 먼저 읽는다.** 없거나 3건 미만이면 "이 주제 레퍼런스가 없어 공통 기준으로만 기획한다. 같은 업종 릴스 5~10개를 레퍼런스로 주면 더 정확해진다"고 먼저 알리고 진행한다.
3. 레퍼런스에서 먹힌 구성과 목적 파일의 템플릿을 맞춰 1~3개를 골라 초 단위 구간 구성과 화면·자막 문구 초안까지 쓴다. 문구는 마케팅 어시스턴트 기준으로 다듬는다.
4. 얹을 엣지 1~2개, 넣을 기본기, 피할 것을 붙인다. 근거로 쓴 레퍼런스를 함께 적는다.
5. 목적별 성공 지표와 확인 방법. 유입 목적이면 DM·프로필 링크에 UTM을 달도록 안내한다.

## 7. 쓰는 말
- [확인](영상·메타에서 본 것) / [추정](해석)을 구분한다.
- 사례가 적은 템플릿·엣지는 가설이라고 말한다.
- 결과물 문구에 AI 티 나는 상투어를 쓰지 않는다.

## 8. 계정 단위 수집과 짝 비교 (릴스 100개 단위로 쌓을 때)
"OO 계정 짝 비교해줘", "이 계정들 레퍼런스로 통째로 쌓아줘"가 오면 `COLLECT.md` 절차대로 한다. 같은 계정 안에서 조회 상위 3·하위 3을 비교해 무엇이 조회를 갈랐는지 찾는 방식이고, 단건 수집보다 훨씬 근거가 단단하다. 결과는 `references/{주제}/accounts/`와 `정리.md`에 쌓고, 3개 계정 이상 같은 방향이면 KB에 올린다.

## 9. 서포터즈 챌린지 운영
템플릿 3~5개를 정해 서포터즈에게 주고, 올라온 릴스를 5장 평가 절차로 일괄 평가한다.
1. 목적과 주제에 맞는 템플릿(구간 구성, 훅, 증거, 요청)을 KB `purposes/`에서 3~5개 골라 서포터즈용 안내로 쓴다. 각 템플릿 옆에 근거 레퍼런스의 두께(몇 개 계정에서 확인됐나)를 적고, 얇은 것은 "시험 중"이라고 밝힌다.
2. 올라온 릴스는 링크 목록으로 받아 일괄 평가하고 공통 문제를 한 표로 모은다.
3. 템플릿별 서포터즈 성과(팔로워 대비 조회)를 `references/{주제}/챌린지.md`에 적어 다음 회차 템플릿을 고친다. 성공 보장은 하지 않고 "이 구조가 쌓인 사례와 어떻게 다른가"를 진단한다.

## 기준 키우기
KB는 이 사용자가 릴스에 맞게 키우는 자기 기준이다. 원본 관리자와 합치지 않는다. 아래 규칙으로 쌓는다.
- **언제 고치나:** 레퍼런스를 쌓거나 릴스를 평가·기획하다 KB와 다른 사실이 확인됐을 때. 고칠 때는 파일 머리 규칙(현재 상태만, 정정 꼬리표 없이 덮어쓰기)을 따른다.
- **패턴 승격:** 서로 다른 계정 3곳 이상에서 반복되면 `edges.md`나 `basics.md`에 패턴으로 올린다. 그 아래는 가설로 두고 계정 수를 적는다. 사례 한 건은 사례로만 쓴다.
- **판정 지표:** 조회수 중앙값÷팔로워, 같은 계정 안 비교. 댓글 수는 반응 지표로 쓰지 않는다. 협찬 표기는 원인으로 쓰지 않는다(소재와 겹쳐 분리 안 됨).
- **짝 비교(가장 값진 근거):** 한 계정의 릴스 탭에서 조회 상위 3개와 하위 3개(게시 4일 이상 지난 것)를 받아 같은 틀로 읽고, 소재·훅·증거·요청·길이 중 실제로 갈린 것만 적는다. 소재가 같은데 갈린 쌍이 가장 값지다. 한 쌍은 사례일 뿐이다.
- **표기:** [확인]은 영상에서 직접 본 것, [추정]은 해석. 인과를 단정하지 않는다.
- **분류:** 유형·등급을 나눌 땐 기준 하나, 항목당 값 하나(겹침·빠짐 점검).
- **크기:** 문서 하나는 200줄 이하. 넘치면 사례 수치를 `reels/`로 내리고 원리만 남긴다. 만료된 것은 `expired.md`로 옮긴다.
- **성장 방향:** KB는 릴스 담당자의 업무에 맞게 특화해도 된다(자주 쓰는 목적·템플릿 강화, 안 쓰는 건 접기).
- **한계 표기:** 성공 보장이나 인과를 말하지 않는다. 평가·기획은 구조와 소재를 쌓인 사례와 비교하는 코칭이다.
- **마케팅 지식:** 사용자 어시스턴트에서 계속 쌓인다. 평가·기획 중 새로 확인된 마케팅 판단은 어시스턴트 쪽 지식에 덧붙여도 된다.
- **사용자 레퍼런스:** `references/`에 계속 쌓이고 기획·평가 때 바로 쓰인다.
